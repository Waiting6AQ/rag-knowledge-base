## 一、项目概述

**定位**：面向企业私有文档的智能问答系统——把散落在 PDF / Word / Excel / Markdown 里的知识，变成可检索、可追溯、可多轮对话的知识库。

**要解决的痛点与对应方案**

| 痛点 | 解决方案 | 用户价值 |
| --- | --- | --- |
| 关键词检索换个说法就找不到（"薪资" vs "薪酬待遇"） | 向量语义 + BM25 关键词混合检索，RRF 融合互补 | 同义表达也能召回 |
| 检索结果混入语义无关的内容 | 三层过滤 + CrossEncoder 精排（低分文档直接丢弃） | 回答只基于真正相关的内容 |
| 大模型直接回答会编造，且无出处 | 检索增强生成：只依据文档回答，引用来源随消息落库 | 答案可追溯、可验证 |
| 多轮追问（"它多少钱"）指代不清导致答错 | 查询改写：指代消解 + 措辞优化后再检索 | 多轮对话不失忆 |
| 长对话后上下文超限、答非所问 | 历史消息自动摘要压缩（窗口 8 条 / 保留 4 条） | 长对话稳定，且控制 token 成本 |
| 知识库文档无法维护 | 5 种格式上传 + SHA256 去重 + 删除级联清理索引 | 知识库可持续维护 |
| 多份文档混在一起，通用词跨文档串扰 | 每块正文前置 `[文件名]` 来源标记 | 回答归属清晰 |
| 效果缺少量化依据 | 自建 50 条标注评测集（来源命中 50/50、关键词覆盖率 90.8%） | 有数据支撑系统可用性 |

**核心能力**

- 5 种文档格式解析（PDF / DOCX / XLSX / TXT / MD），自定义 Excel 加载器，递归分块（500 字符 / 重叠 100）
- 三层检索过滤链路：前置过滤 → 混合检索（RRF 融合）→ 后置过滤 → CrossEncoder 精排
- 多轮对话：指代消解改写 + 超量消息自动摘要（窗口 8 条 / 保留 4 条），会话状态持久化
- Token 级 SSE 流式输出：打字机效果 + 管线进度 + 引用来源实时展示
- 引用来源随消息落库，历史会话回看仍可见出处
- SHA256 文件级去重、上传大小/类型校验、全链路异常降级
- 完整业务形态：JWT 登录认证、会话管理、文档管理，前后端分离

**技术栈**

| 层 | 技术 |
| --- | --- |
| 前端 | Vue 3 / Vite / axios / markdown-it + DOMPurify |
| 业务后端 | Spring Boot 3.5 / MyBatis / MySQL / JWT（jjwt）+ BCrypt / RestClient |
| AI 引擎 | Python / FastAPI / LangGraph / LangChain / ChromaDB / CrossEncoder（bge-reranker）/ 通义千问 |
| 部署 | Docker 多阶段构建 / docker compose / 镜像仓库（ACR）/ 阿里云 ECS |

## 二、系统架构

```
浏览器（Vue 3 单页应用）
    │  JWT 鉴权（Authorization: Bearer <token>）
    ▼
Spring Boot 业务后端（:8081）—— 唯一对外网关
    ├─ 用户体系：注册 / 登录 / 角色（user + role 简化 RBAC）
    ├─ 会话管理：会话归属校验（用户只能访问自己的会话）
    ├─ 文档管理：上传校验 → 转发引擎解析；列表 / 删除代理
    ├─ AI 转发：SSE 流式透传（注入 X-User-Id 可信头）
    ▼
Python RAG 引擎（:8000）—— 内部 AI 能力层，不对外暴露
    └─ LangGraph 5 节点管线 + ChromaDB 向量库 + SQLite checkpoint
```

**为什么分两层（Java 网关 + Python 引擎）**

| 考量 | 说明 |
| --- | --- |
| 职责分离 | Java 擅长业务系统（鉴权、事务、审计），Python 在 AI 生态最成熟，各用所长 |
| 安全边界 | 引擎不对外暴露端口，所有流量经网关；用户身份由网关注入，引擎不感知用户 |
| 可替换性 | AI 引擎可独立升级/替换（换模型、换检索策略），业务侧接口契约不变 |
| 归属清晰 | 用户与会话归属数据在业务侧 MySQL（权威记录），引擎只负责 AI 能力 |

## 三、RAG 管线设计（LangGraph 5 节点）

```
START → summarize → rewrite_query → retrieve_documents → generate_answer → evaluate_confidence → END
```

| 节点 | 职责 | 设计意图 |
| --- | --- | --- |
| `summarize` | 消息超量时增量压缩历史（窗口 8 条 / 保留 4 条） | 长对话不丢关键信息，同时控制 token 成本 |
| `rewrite_query` | 多轮指代消解：把"那病假呢"改写为独立完整的问题 | 检索质量取决于 query 质量，含糊指代会直接导致召回失败 |
| `retrieve_documents` | 三层过滤 + 混合检索 + 精排 | 见第四节 |
| `generate_answer` | 基于上下文生成回答（无相关文档时降级为普通聊天） | 有据可依，避免无文档时强行作答 |
| `evaluate_confidence` | LLM 五级锚点自评置信度（无上下文时跳过） | 给用户一个可信度参考信号 |

**为什么用 LangGraph 而不是手写流程**：状态显式化（每个节点读写同一份 State，便于调试与扩展）、条件路由天然支持、checkpoint 持久化开箱即用、流式事件与节点进度可直接挂接。

## 四、检索链路：三层过滤 + 混合检索

```
用户问题
    │
    ▼
┌──────────────┐  向量检索 top-20，建 score_map（距离 < 1.5）
│  前置过滤     │  无相关文档 → 直接切普通聊天，不做无意义的检索
└──────┬───────┘
       ▼
┌──────────────┐  向量检索（k=5）+ BM25（k=3）→ RRF 融合（权重 0.6 / 0.4）
│  混合检索     │  语义匹配补"同义不同词"，关键词匹配补"专有名词/编号"
└──────┬───────┘
       ▼
┌──────────────┐  用 score_map 剔除 BM25 混入的、无向量得分的文档
│  后置过滤     │  纯关键词命中但语义无关的内容在此清除
└──────┬───────┘
       ▼
┌──────────────┐  CrossEncoder 联合编码精排，分数 < 0.3 直接丢弃
│  CrossEncoder│  粗排判断相似度，精排判断相关性
└──────┬───────┘
       ▼
   相关文档 → 构建 context → 生成回答（附引用来源）
```

**每一层为什么存在**（都是被真实问题逼出来的，见复盘第 1 条）

- **混合检索**：纯向量会漏掉"专有名词、编号、型号"这类精确匹配；纯 BM25 会漏掉同义表达。两者 RRF 融合互补。
- **前置过滤**：避免"知识库里根本没有这个问题"时仍强行检索、把无关文档喂给模型。
- **后置过滤**：BM25 只要命中关键词就返回，不管语义是否相关——用向量得分表把这类噪声剔除。
- **CrossEncoder 精排**：双塔向量模型"分别编码再算距离"，精度有限；CrossEncoder 把 query 和文档拼在一起联合编码，判断更准，代价是慢——所以只对少量候选做精排。

**Embedding 与 CrossEncoder 的分层选型**

| | Embedding | CrossEncoder |
| --- | --- | --- |
| 模型 | `text-embedding-v4`（云端 API） | `BAAI/bge-reranker-base`（本地 CPU） |
| 调用频率 | 低（仅文档上传时） | 高（每次问答） |
| 放哪 | API（节省本地资源） | 本地（节省网络往返与调用费用） |

调用频率决定部署位置：低频走 API，高频走本地。Embedding 负责海选，CrossEncoder 负责精选。

## 五、工程化实践

**1. 对话归属在业务侧，AI 引擎不感知用户**

`user_id ↔ conversation_id` 映射存于业务 MySQL；引擎只按 `conversation_id` 维护多轮上下文（会话级 checkpoint，无用户体系）。网关注入 `X-User-Id` 可信头（预留数据隔离/审计）。好处：权限判定集中在网关一处，引擎可无状态扩展。

**2. SSE 原样透传（而不是逐事件翻译）**

Java 网关把引擎的 SSE 字节流逐行原样转发给前端，只劫持 `done` 事件附加 `session_id`。此前 Java 曾"翻译"每个事件再重发，格式细节不一致导致前端解析整体失效——原样透传让格式只有一处定义。

**3. 引用来源随消息落库**

`sources` 事件在回答前到达时即被旁路记录并随 AI 消息写入 MySQL，历史会话回看仍能显示引用来源——刷新页面、重新登录都不丢。

**4. BM25 索引缓存（性能）**

BM25 需全量文档构建倒排索引。早期实现每次查询都全量拉取重建，文档量一大即成瓶颈。现改为共享缓存对象：首次构建、文档变更时失效、下次查询重建——开销从"每次查询"降到"每次文档变更"。

**5. chunk 来源注入（检索质量）**

每个分块正文前置 `[文件名]` 标识，使检索与生成都能感知 chunk 归属，多文档场景下通用词不再跨文档串扰（见复盘第 2 条）。

**6. 事务边界（一致性）**

一轮问答的"用户消息 + AI 回复 + 标题更新"收进一个事务（独立 Service bean，跨 bean 调用保证 `@Transactional` 生效）；删除会话时"删消息 + 删会话"同事务。事务只圈落库段，不包含 AI 网络调用。

**7. 并发模型审计（性能）**

对引擎与网关做过一次异步审计，修复了三层并发瓶颈：

| 层次 | 问题 | 修复 |
| --- | --- | --- |
| 事件循环阻塞 | 文档上传的"解析 / 分块 / Embedding 调用 / 写库"整段是同步代码，跑在 async 路由里会独占事件循环——上传大文件期间，其他请求（含正在流式输出的对话）全部卡住 | 重活抽成同步方法、用 `run_in_threadpool` 移出事件循环；纯同步的路由改回 `def` 交给框架线程池 |
| 线程池占用 | LLM 节点是同步实现，每次调用占住共享线程池的一个位子 5-15 秒（2 核机器上该池仅 6 个位） | 4 个 LLM 节点改为异步（`ainvoke` / `astream`），等待期间不占线程；检索节点保持同步（本地 CPU 工作，无异步 API） |
| 网关并发上限 | Spring Boot 默认异步执行器为「core 8 + 无界队列」，队列永不填满意味着线程永不扩容，SSE 并发被卡在 8 条 | 显式配置 core / max / 有界队列 |

实测（10 条并发流式请求）：**首 token 延迟的最大/最小比值从 4.0x 降至 1.5x，总耗时降低 38%**。

## 七、项目复盘

> 以下为开发过程中真实遇到并解决的问题，按"问题 → 定位 → 解决 → 沉淀"记录。选取标准：体现设计权衡、边界处理或数据一致性的问题，而非单纯的 API 使用细节。

**1. 检索相关性：三层过滤链路是被问题逼出来的**

- **问题**：问"你好"，回答引用了无关文档；问"圣枪哥输过吗"，师徒关系文档混入来源；而简历里的中文姓名反而查不到。
- **定位**：向量检索总是返回 top-k、不做相关性判断；BM25 只做关键词匹配，实体重叠就召回；相似度阈值 1.0 对"中文姓名 + 短查询"组合过严。
- **解决**：逐步形成三层——前置过滤（距离阈值粗筛，建 score_map）→ 后置过滤（用 score_map 剔除 BM25 混入的无分文档）→ CrossEncoder 精排 + 0.3 阈值；阈值从 1.0 放宽到 1.5，由后两层兜底剔除真正无关的文档。**无相关文档时主动降级为普通聊天**，不强行检索作答。
- **沉淀**：**召回与过滤是两件事**；每层过滤都要有明确的"剔除理由"，阈值必须基于实测数据调，不能凭直觉。

**2. 多文档场景下的语义串扰（来源必须进入检索链路）**

- **问题**：知识库中只有一份公司手册时问"薪资"能正确回答；再上传另一家公司的文档后，两份"薪资"内容互相串——chunk 正文里没写公司名，检索和生成都无法区分归属。
- **定位**：检索只匹配正文，文件名元数据此前只用于回答后打标签，不参与检索与生成。
- **解决**：分块时给每块正文前置 `[文件名]` 标识，让来源参与语义匹配与生成；提示词中说明 `[来源]` 的含义（只陈述事实、不加行为指令）。
- **沉淀**：**多主体场景下，来源标识必须进入检索与生成链路，不能只做展示**——这是知识库支持多客户/多主体的前提。

**3. Prompt 的"过度引导"反而降低准确性**

- **问题**：给 RAG 提示词加"可做逻辑推导，但不得引入外部知识"后，模型既编造了文档外的信息，又把"waiting 的徒弟是圣枪哥"说反了。
- **定位**：对比测试显示，"只使用上下文"版本回答干净、关系正确；"推导 + 不得引入"版本让模型在模糊边界自行发挥。
- **解决**：回退为简洁的"只使用提供的上下文信息来回答问题"，不做额外引导。
- **沉淀**：**对 LLM 的约束要具体、可执行，宁少勿多**；规则之间的留白会成为模型自由发挥的空间。

**4. 模型能力差异：用对比实验定位，而非猜测**

- **问题**：多轮追问"它的作用是什么"时回答为空。
- **定位**：加 trace 定位到改写节点返回空字符串 → 相关性过滤挡掉模糊查询 → 普通聊天模式再次返回空；再做"模型 × 温度"矩阵对比：flash 系列全部为空，35b/max 系列正常——确认是模型对含来源标注的历史不兼容，与温度无关。
- **解决**：更换默认模型 + 改写节点保留空值 guard 防御。
- **沉淀**：**不确定的问题先设计可对比的实验**，比反复猜测快得多，且结论可复现。

**5. 流式防护必须覆盖"空流"**

- **问题**：偶发界面转圈、状态栏显示"回答完成"、刷新后该 AI 消息为空白。
- **定位**：用证据链区分"前端丢数据"与"后端空流"——刷新后仍空白说明 checkpoint 里存的就是空字符串（checkpoint 由后端节点写入，与前端无关）。
- **解决**：流正常结束后检查 `if not full_answer`，补写降级提示并推送前端。
- **沉淀**：**流式调用的防护要覆盖三种情况——异常、空流、正常**；只防异常会产生"静默空消息"这类最难排查的故障。

**6. 上传接口设计：单文件接口 + 前端循环**

- **背景**：FastAPI 支持一次接收多个文件，但本项目采用"后端只接收单文件 + 前端逐个调用"。
- **理由**：① 分块与向量化属于重量级 I/O 操作，批量接收会让浏览器长时间等待直至超时；② **错误隔离**——文件 A 成功、文件 B 重复（409）时，用户能看到每个文件的独立结果，批量接收则面临"部分成功如何处理"的困境；③ 单文件接口更通用，第三方调用无需组装数组。
- **配套**：上传是"先写文件、后写向量库"的多步操作，失败时补偿清理（删孤儿文件 + 清半索引 chunk），不留脏数据。
- **沉淀**：**接口粒度要服务于失败处理**——让每次调用都是独立可解释的单元。

## 九、当前局限与演进方向

**当前定位**：单机演示部署（单实例），已完成端到端验证与 10 并发流式实测（见「工程化实践 7」）；容量适合小规模试用与演示。

**已知瓶颈**

| 环节 | 现状 | 影响 |
| --- | --- | --- |
| Python 引擎 | 单进程单事件循环（uvicorn 单 worker），已完成并发审计（见工程化实践 7） | LLM 等待不再占用线程池；剩余瓶颈是本地 CPU 工作（CrossEncoder 重排）与单进程事件循环本身 |
| Java 网关 | 单实例；SSE 异步执行器已显式配置（core 32 / max 64 / 有界队列 32） | 并发流上限已从默认的 8 条解除；进一步提升需多实例 + 负载均衡 |
| 会话状态 | SQLite checkpoint（单文件、写事务串行） | 小并发无感；**水平扩展的硬约束**——文件级数据库无法多实例共享 |
| 业务库 | MySQL 单实例，连接池默认上限 | 并发数据库操作超过池上限时排队 |
| 外部依赖 | 大模型 / Embedding API | 账号级 QPS 限制 |
| 机器资源 | 2 核 4G 单机 | CPU（重排推理）与内存（模型）上限 |

**演进路径**（按优先级）

1. **先观测再扩容**：接入监控（请求延迟、错误率、并发数、引擎队列深度），有数据再决定扩容方向；
2. **限流与排队**：网关层令牌桶限流 + 超载排队，让请求等待而非打挂服务；
3. **状态外移**：SQLite checkpoint → Postgres（LangGraph 官方 PostgresSaver）—— 多实例的**前置条件之一**；
4. **向量库服务化**：ChromaDB → pgvector / Milvus，支持多实例共享与数据量增长 —— 多实例的**前置条件之二**；
5. **引擎多实例**：uvicorn 多 worker / 多容器 + Nginx 负载均衡（**依赖 3、4 完成**：文件级数据库与本地向量库均无法跨进程/实例共享，直接加 `--workers` 会破坏数据一致性）；
6. **重排服务化**：CrossEncoder 独立进程 / GPU 服务，或改用 API 版 rerank；
7. **成本控制**：LLM 响应缓存、按用户配额。
